# 辩论机制技术方案 (2026-07-01)

## 背景

HeavySkill K=8 审查发现：当前报告(58/100)的核心差距是"投资洞察生成机制"缺失。
单次LLM生成产出的是"数据罗列"而非"投资分析"。

## 核心设计

Bull→Bear→PM 三角色辩论，嵌入章节写作阶段:

```
_write_chapters() 循环体
├─ ch01-ch09: _debate_chapter()
│   ├─ Step 1: _debate_bull_draft()
│   │   └─ 复用 _build_chapter_prompt() + BULL_SYSTEM
│   ├─ Step 2: _debate_bear_challenge()
│   │   └─ 精简prompt: bull_draft + contract + 关键数据摘要
│   └─ Step 3: _debate_pm_synthesis()
│       └─ 输出符合 contract.must_answer 结构
└─ ch00/ch10: 保持原有单次生成
```

## Prompt 设计

### Bull
- 每个论点必须有数据支撑，标注来源
- 禁止模糊词汇
- 必须包含"预期差"和"催化剂"
- 输出格式：核心看多论点 + 投资摘要

### Bear
- 逐条质疑看多论点
- 必须给出替代估值
- 必须列出至少3个被忽略的风险
- 输出格式：逐条反驳 + 替代估值 + 关键风险

### PM
- 评估正反双方论点质量
- 确信度构成：数据支撑度 + 逻辑严密性 + 预期差大小
- 触发条件：至少3个上行 + 3个下行，必须可量化可监控
- 输出必须符合 contract.must_answer 结构

## 降级策略

| 失败步骤 | 降级行为 |
|---------|---------|
| Bull 失败 | 降级到原有单次生成 |
| Bear 失败 | 使用 Bull 的输出 |
| PM 失败 | 使用 Bull 的输出 |

## 成本

- 每章3次LLM调用(原来1次)
- ch01-ch09 = 27次(原来9次)
- 预计额外耗时: +15分钟
- 实际token消耗约2.5x(Bear/PM prompt较短)

## HeavySkill 审查结论

- 解决"怎么想"的问题(分析深度、逻辑完整性): 中高
- 不能解决"算什么"的问题(PE计算、DCF、数据一致性): 低
- 单独使用可提升至75-78分
- 与P0数据修复结合可提升至78-82分

## 关键教训

1. 辩论机制不是替代P0-P2方案，而是互补
2. 辩论需要估值数据作为量化锚点(L1.5必须在L2之前)
3. Bear Prompt必须包含"替代估值"要求
4. PM输出必须符合contract结构(与审计模块兼容)
5. 单轮辩论是v1的合理选择，Phase 2再考虑多轮
