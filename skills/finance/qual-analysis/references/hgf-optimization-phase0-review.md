## 问题诊断

| 问题 | 表现 | 影响 |
|------|------|------|
| 开始时缺少技术文档审查 | 直接开始编码，需求不明确 | 返工率高 |
| 代码审查不够全面深入 | 只检查语法，不检查逻辑 | 功能缺陷遗漏 |
| 缺乏对照技术文档审查 | 代码与文档脱节 | 实现偏离设计 |
| 审查标准不统一 | 审查质量参差不齐 | 无法保证一致性 |

---

## 优化方案

### Phase 0: 技术文档审查（新增）

**文档包要求（6份）**：
1. PROPOSAL.md — 需求、目标、范围、验收标准
2. ARCHITECTURE.md — 架构设计、模块划分、数据流
3. API-CONTRACTS.md — 所有接口定义
4. DATA-SOURCES.md — 数据源清单、降级策略
5. TEST-STRATEGY.md — 测试策略、验收条件
6. RISK-REGISTER.md — 风险登记表

**Gate 0通过标准**：
- [ ] 所有文档齐全且格式规范
- [ ] 验收标准是可量化、可测试的
- [ ] 所有外部依赖已实际验证可达
- [ ] 数据源已用真实ticker测试过连通性
- [ ] 降级策略已明确定义（禁止静默降级）
- [ ] 评审专家双方签字确认

### 逐模块审查流程（5步）

```
Step 1: 代码静态审查（语法/风格/命名）
Step 2: 架构一致性审查（对照技术文档）
Step 3: 功能验证（真实执行）
Step 4: 对照审查表（逐函数对照）
Step 5: 审查结论（PASS/CONDITIONAL_PASS/REJECT）
```

### 审查标准

| 等级 | 定义 | 处理方式 |
|------|------|----------|
| P0 | 阻塞级：功能不可用或数据错误 | 一票否决 |
| P1 | 严重：功能缺陷或安全隐患 | 必须修复 |
| P2 | 一般：代码质量或规范问题 | 建议修复 |
| P3 | 轻微：优化建议 | 可选修复 |
