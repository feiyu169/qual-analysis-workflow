## 核心内容

### 角色定义

| 角色 | 职责 | 权限 | 决策范围 |
|------|------|------|----------|
| 执行者 | 编写代码、实现功能 | 无审查权限 | 实现细节 |
| 审查专家 | 独立第三方审查 | 一票否决权（P0问题） | 通过/不通过 |
| 编程专家 | 技术方案设计、接口定义 | 技术决策权 | 技术选型、架构设计 |
| 协调者 | 流程协调、进度跟踪 | 流程管理权 | 流程调整、进度安排 |

### Phase 0: 技术文档审查（新增）

6份技术文档：
1. PROPOSAL.md — 需求、目标、范围、验收标准
2. ARCHITECTURE.md — 架构设计、模块划分、数据流
3. API-CONTRACTS.md — 所有接口定义
4. DATA-SOURCES.md — 数据源清单、降级策略
5. TEST-STRATEGY.md — 测试策略、验收条件
6. RISK-REGISTER.md — 风险登记表

Gate 0 通过标准：
- 所有文档齐全且格式规范
- 验收标准是可量化、可测试的
- 所有外部依赖已实际验证可达
- 数据源已用真实ticker测试过连通性
- 降级策略已明确定义（禁止静默降级）
- 评审专家双方签字确认

### Phase 1-5: 逐模块审查（5步流程）

1. 代码静态审查（语法、风格、命名）
2. 架构一致性审查（对照技术文档）
3. 功能验证（真实执行）
4. 对照审查表（需求→代码映射）
5. 审查结论（PASS/CONDITIONAL_PASS/REJECT）

### 审查标准

| 等级 | 定义 | 处理方式 |
|------|------|----------|
| P0 | 阻塞级：功能不可用或数据错误 | 一票否决，必须修复 |
| P1 | 严重：功能缺陷或安全隐患 | 必须修复 |
| P2 | 一般：代码质量或规范问题 | 建议修复 |
| P3 | 轻微：优化建议 | 可选修复 |

### 审查不通过处理

最多3轮迭代，超过3轮升级到用户决策。

## 三人小组模式

- 审查专家：给出审查流程和具体要求
- 编程专家：给出技术文档的具体结构要求
- 协调者：编制实现的具体技术方案

## HeavySkill 迭代模式

```
Round 1: 提出方案 → HeavySkill K=8 审查 → 记录问题
Round 2: 按审查意见修改 → 再次审查 → 记录改进
Round N: 直到审查意见收敛（无新P0问题）
```
