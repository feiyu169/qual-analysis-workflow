# HeavySkill 迭代审查模式 — v1.0→v6.0 经验总结

## 模式概述

当需要对技术方案进行多轮审查时，使用HeavySkill K=8进行迭代审查，每轮根据审查意见修改后重新提交。

## 执行流程

```
Round 1: 提交方案v1 → HeavySkill审查 → 收集意见
Round 2: 根据意见修改v2 → HeavySkill审查 → 收集意见
...
Round N: 方案vN通过 → 进入实施
```

## 经验教训

### 1. 审查意见必须逐条落实
- v3.0审查发现"架构过于复杂"→ v4.0简化推理链
- v5.0审查发现"接口签名缺失"→ v6.0补齐完整签名
- 每轮审查意见必须在下一轮中体现

### 2. 核心问题优先解决
- v1.0: 深度标准无量化定义 → 最优先
- v2.0: 推理引擎是黑盒 → 第二优先
- v3.0: 架构过于复杂 → 第三优先
- 按严重程度排序，逐轮解决

### 3. 避免过度设计
- v3.0引入过多概念（3条推理链+5维度+3维降级）
- v4.0简化为2条推理链
- v5.0进一步简化为单链3阶段
- 每轮都在做减法

### 4. 接口契约必须完整
- v5.0只列出接口名，无方法签名
- v6.0补齐完整签名+输入输出类型+异常
- 接口契约是代码质量的基础

### 5. 实测验证不可省略
- v6.0实施后用万华化学和快手实测
- 发现PB计算错误、口径不一致等问题
- 实测是检验方案的唯一标准

## 审查维度模板

```markdown
## 审查维度
1. **架构简洁性** — 模块数量是否最少？职责是否单一？
2. **代码质量** — 错误处理是否完整？类型注解是否完整？
3. **投资分析深度可行性** — 深度标准是否可量化？推理引擎是否可行？
4. **规范性** — 是否符合现有代码风格？是否向后兼容？
```

## 输出格式模板

```markdown
### 审查结论
通过/不通过

### 四维度评分
| 维度 | 评分 | 关键建议 |
|------|------|----------|

### 共识结论
> "引用审查共识"

### 下一步行动
| 优先级 | 行动项 | 预计工时 |
```

## 实测案例

### 快手(1024.HK) v1.0→v6.0
- v1.0: 不通过（深度标准无量化定义）
- v2.0: 4.0/5（推理引擎是黑盒）
- v3.0: 待定（架构过于复杂）
- v4.0: 待定（接口契约待补充）
- v5.0: 待定（因果建模方法待明确）
- v6.0: 可开发（完整签名+证伪公式+因果方法论）

### 万华化学(600309.SH) + 快手 实测
- 两份报告均92分/A级
- 发现PB计算错误、口径不一致等5个问题
