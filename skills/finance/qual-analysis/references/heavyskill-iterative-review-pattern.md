# HeavySkill 迭代审查模式

> 2026-07-01 实证验证：快手分析报告质量提升方案 v1.0→v5.0

## 模式概述

当需要验证技术方案质量时，使用 HeavySkill K=8 进行多轮迭代审查：

```
Round 1: 提出方案 → HeavySkill 审查 → 记录问题
Round 2: 按审查意见修改 → 再次审查 → 记录改进
Round N: 直到审查意见收敛（无新P0问题）
```

## 实证案例：v1.0→v5.0 演进

| 版本 | HeavySkill评分 | 核心改进 | 剩余关键问题 |
|------|----------------|----------|--------------|
| v1.0 | 不通过 | 问题诊断准确 | 深度标准无量化定义 |
| v2.0 | 4.0/5 | 深度标准量化、Feature Flag | 推理引擎是黑盒 |
| v3.0 | 待定 | 借鉴GitHub项目、推理链设计 | 架构过于复杂 |
| v4.0 | 待定 | 简化推理链、规则引擎化 | 接口契约待补充 |
| v5.0 | 待定 | 单链3阶段、完整接口契约 | 因果建模方法待明确 |

## 每轮审查的四个维度

1. **架构简洁性** — 模块数量、职责单一、依赖清晰
2. **代码质量** — 错误处理、类型注解、测试策略
3. **投资分析深度可行性** — 深度标准可量化、推理引擎可行、数据验证充分
4. **规范性** — 代码风格兼容、向后兼容、可回滚

## 审查意见处理优先级

```
P0: 必须在下一版本解决（阻塞性问题）
P1: 应在下一版本解决（重要但不阻塞）
P2: 可在后续迭代解决（优化项）
```

## 关键教训

1. **不要一次设计太多**：v3.0 引入了6个GitHub项目借鉴，导致架构过于复杂。v4.0 简化为2条推理链后审查意见明显改善。

2. **接口契约必须早期定义**：v4.0 审查指出"接口定义缺失"是主要问题。v5.0 补充了完整方法签名后代码质量维度提升。

3. **量化输出要避免"假精确"**：v5.0 将精确数值改为有序分级(强/中/弱)+置信区间，更符合投资分析的不确定性特征。

4. **证伪指标权重需足够高**：从5%提升至15%并设最低阈值强制降级，是v5.0的重要改进。

5. **审查意见收敛判断**：当连续两轮审查意见中无新增P0问题，且改进建议主要是P2级别时，可认为方案已具备开发条件。

## 与三角色讨论会的配合

最佳实践是先用三角色讨论会形成方案，再用 HeavySkill 审查验证：

```
三角色讨论会（投资专家+编程专家+协调者）
    ↓ 输出方案初稿
HeavySkill K=8 审查
    ↓ 输出审查意见
三角色讨论会（按意见修改）
    ↓ 输出修订方案
HeavySkill K=8 复审
    ↓ 直到收敛
```
