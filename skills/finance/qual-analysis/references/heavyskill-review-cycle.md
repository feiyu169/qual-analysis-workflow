# HeavySkill迭代审查循环模式

## 适用场景
当技术方案需要通过HeavySkill审查时，使用此迭代模式。

## 迭代模式

### 标准流程
```
技术方案v1.0 → HeavySkill审查 → 识别问题 → 修改 → v2.0 → 审查 → ... → 通过
```

### 实测收敛轨迹（快手案例）
| 版本 | 评分 | 核心改进 | 剩余问题 |
|------|------|----------|----------|
| v1.0 | 不通过 | 问题诊断准确 | 深度标准无量化定义 |
| v2.0 | 4.0/5 | 深度标准量化、Feature Flag | 推理引擎是黑盒 |
| v3.0 | 待定 | 借鉴GitHub项目、推理链设计 | 架构过于复杂 |
| v4.0 | 待定 | 简化推理链、规则引擎化 | 接口契约待补充 |
| v5.0 | 待定 | 单链3阶段、接口签名 | 因果建模方法待明确 |
| v6.0 | 可开发 | 完整签名、证伪公式、ADR | 原型验证 |

### 收敛策略
1. **先广后窄**：v1-v3探索架构方向，v4-v6收敛实现细节
2. **每轮聚焦1-2个核心问题**：不要试图一次解决所有问题
3. **保留前轮优点**：修改时不要破坏已通过的部分
4. **HeavySkill审查必须内联内容**：不要引用文件路径，直接内联关键技术内容

### HeavySkill查询优化技巧
1. 将文档关键内容内联到query中（子代理无法读取本地文件）
2. 明确列出审查维度和评分标准
3. K=8标准审查，K=16关键审查
4. 输出JSON便于程序化解析

## 三人讨论会模式

### 角色分工
- **投资分析专家**：优化思维链和逻辑链，给出深度标准
- **协调者**：给出实现技术文档
- **编程专家**：审核代码可行性

### 并行执行
使用delegate_task的batch模式，3个任务并行执行，节省时间。

### 合成方法
协调者综合三方意见，形成最终技术文档，再提交HeavySkill审查。

## HGF Gate执行模式

### 标准流程
```
Phase 1: 创建模块 → 编译验证 → 独立评审专家审查 → 通过/修复
Phase 2: 创建模块 → 编译验证 → 独立评审专家审查 → 通过/修复
...
```

### 评审原则
- 严格对照技术方案，有所偏离不进行下一步
- 检查每个文件是否符合技术方案要求
- 检查接口签名、类型注解、异常处理

### 实测案例（快手v6.0实施）
- Phase 1: 5个模块，评审9/10，一次通过
- Phase 2: 4个模块，评审通过（Granger检验简化标注）
- Phase 3: 3个模块，首次不通过（加权评分机制错误）→修复→通过
- Phase 4: 集成测试，一次通过
