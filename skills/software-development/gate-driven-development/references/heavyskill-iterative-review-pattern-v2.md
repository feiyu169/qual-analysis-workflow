# HeavySkill迭代审查模式 v2 (2026-07-29验证)

## 概述

技术方案设计必须经过HeavySkill K=8多轮迭代审查，直到P0问题清零且评分≥85分。

## 双专家并行审查模式

每次审查启动2位专家并行：

```
delegate_task(tasks=[
  {goal: "投资分析专家: 从买方严肃性角度评审", role: "leaf"},
  {goal: "架构编程专家: 评审技术架构可行性", role: "leaf"}
])
```

**评分规则**: 综合评分 = (投资专家分 + 架构专家分) / 2

## 收敛轨迹 (实测v3.0→v3.2.2)

```
v3.0 (72分) — 基础框架，13个缺陷未解决
  ↓ +6 (解决估值计算问题)
v3.1 (78分) — 估值引擎(85分)，回答14个架构问题
  ↓ +4 (补充数据治理+审计层)
v3.2 (83分) — 四层防护闭环，2个P0阻断
  ↓ +2 (解决权威冲突+测试策略)
v3.2.1 (85.5分) — 达到机构级标准
  ↓ +1 (决策矩阵+终值仲裁)
v3.2.2 (86.5分) — 可进入实施
```

**关键发现**: 
- 每轮+2~6分，P0问题必须清零才能进入实施
- v3.1是"估值引擎"而非"质量保障体系"——必须补全所有层
- v3.2是"四层防护闭环"——数据治理+估值约束+逻辑综合+质控验证

## 审查意见处理规则

1. **两位专家意见100%采纳**: 除非有明确理由，否则全部采纳
2. **P0问题必须清零**: 有P0阻断问题不能进入实施
3. **回答必须具体**: 不能只说"已解决"，必须给出代码/配置/规则
4. **再次审查确认**: 回答后必须再次HeavySkill审查

## 权威冲突决策矩阵 (v3.2.2验证)

当多层质量系统并行时，必须定义：

```
┌─────────────────────────────────────────────────────────────┐
│ 场景                │ 模式    │ 规则                        │
├─────────────────────────────────────────────────────────────┤
│ L1通过, L2通过      │ -       │ 直接通过                    │
│ L1通过, L2失败      │ 投票    │ L1(0.7) vs L2(0.3)         │
│ L1失败, L2任意      │ 级联    │ L1失败阻断, L2跳过          │
│ L3发现FATAL         │ 否决    │ L3一票否决                  │
│ L3发现ERROR         │ 投票    │ L3权重=0.5, 与L1加权        │
│ L3发现WARN          │ -       │ 仅记录, 不影响结果          │
└─────────────────────────────────────────────────────────────┘
```

## 终值仲裁阈值 (v3.2.2验证)

```
| 差异范围 | 选定方法 | 置信度 | 额外要求 |
|----------|----------|--------|----------|
| < 10% | 取均值 | high | 无 |
| 10-25% | 取保守(较低值) | medium | 无 |
| 25-50% | 取保守+敏感性分析 | low | 必须展示敏感性矩阵 |
| ≥ 50% | 阻断 | - | 需人工审查 |
```

## 关键教训

1. **不要一次设计太多**: v3.0试图一次解决所有问题，结果每个都不够深入
2. **先回答所有问题再提交**: 14个架构问题必须全部回答，不能遗漏
3. **权威冲突必须有决策矩阵**: 多层系统并行时，必须定义谁是权威
4. **测试策略必须具体**: 84个用例+95%通过率，不能只说"有测试"
5. **保守优先原则**: 终值仲裁、估值口径等，取保守值而非乐观值
