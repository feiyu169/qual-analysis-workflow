# HeavySkill 技术文档迭代审查工作流

## 适用场景

对技术方案/架构文档进行多轮迭代审查，每轮用HeavySkill K=8审查→修订→再审查，直到收敛。

## 标准流程

### 第1轮：K=4 快速审查
- 目标：发现主要问题，确定改进方向
- 查询：将文档内容内联到query，指定三个审查维度
- 耗时：约90秒

### 第2轮起：K=8 深度审查
- 目标：发现细节问题，验证改进效果
- 每轮修订必须明确回应上轮审查发现的问题
- 耗时：约120-150秒

### 收敛判断
- 三维度评分稳定（波动<0.5分）
- 无新的P0级问题提出
- 共识答案趋向一致

## 查询构建模板

```
请审查[文档名称]，从三个维度进行评估：
1. 有效性提升：方案是否真正能提升[目标系统]的有效性？
2. 架构简洁：方案是否会使[目标系统]架构更简洁？
3. 代码质量：方案是否能提升代码质量？
请给出具体评分和改进建议。
```

**关键**：使用 `--include-file` 将文档内容传入，不要仅传文件路径（子代理无法读取本地文件）。

## 评分追踪表

| 版本 | 有效性 | 简洁性 | 代码质量 | 主要改进 |
|------|--------|--------|----------|----------|
| V1   | -      | -      | -        | 初始方案 |
| V2   | 8/10   | 5/10   | 8/10     | 加法过多，简洁性下降 |
| V3   | 7.5/10 | 9/10   | 6.5/10   | 做减法，简洁性提升 |
| V4   | 8/10   | 8.5/10 | 7.5/10   | 清单计分卡+Gate增强 |
| V5   | 8.5/10 | 8.5/10 | 8/10     | 证据关联+统一扩展接口 |

## 从本次迭代总结的规律

1. **先做减法再做加法**：V2加法过多导致简洁性暴跌(5/10)，V3做减法后简洁性飙升(9/10)
2. **架构简洁与功能丰富存在张力**：新增功能必然增加复杂度，关键是"替代而非叠加"
3. **代码质量需区分两个层面**：工具自身代码质量 vs 对产出代码质量的提升
4. **量化指标必须可被验伪**：空洞预测(如"Bug减少40%")会被审查否决
5. **每轮修订必须回应上轮问题**：否则审查会重复指出相同问题

## 常见审查维度（技术文档）

1. **有效性提升**：建议是否真正能解决问题？预期效果是否有数据支撑？
2. **架构简洁**：建议是做加法还是减法？是否引入不必要的复杂度？
3. **代码质量**：示例代码是否可运行？异常处理是否完善？是否有硬编码？

## 避坑指南

- 不要一次性提交大改：每轮聚焦2-3个核心改进点
- 不要忽略审查中的"轻微不足"：下轮审查可能会升级为主要问题
- 不要过度承诺预期效果：保守估计+可被验伪的假设更受认可
- 评分卡/阈值等参数需提供校准依据：否则审查会质疑其有效性
