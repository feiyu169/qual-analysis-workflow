# V1→V2→V3 迭代审查反模式 (Verified 2026-06-20)

## 反模式：修订说明作为附录，不整合到方案正文

```
V1 (初始方案) → HeavySkill → 附意见通过 → 4 P0 问题
V2 (修订说明附加在末尾) → HeavySkill → ❌ 不通过
  原因："修订说明只是愿望清单，方案正文仍是 V1 原貌"
V3 (完整整合版) → HeavySkill → ✅ 附意见通过 → 4 P0 已修复
```

## 根因

V2 只是将修复代码片段附加在文档末尾，没有修改方案正文中的数据模型、引擎代码和配置系统。HeavySkill 审查的是方案正文，不是附录。

## 教训

1. 修复必须整合到方案正文中，不能作为附录
2. 数据模型（如 Issue、Severity）必须同步扩展
3. 配置系统必须包含新增的开关和参数
4. 测试用例必须覆盖新增逻辑

## 正确做法

```
V1 (初始方案) → HeavySkill 审查 → 提取 P0/P1 问题
V2 (完整整合版) → HeavySkill 审查 → 验证修复 + 提取新问题
V3 (终版方案) → HeavySkill 审查 → 确认全部通过
```

## 案例

HeavySkill 优化方案审查（2026-06-20）：
- V1: 附意见通过，4 个 P0 问题
- V2: 不通过，修订未整合
- V3: 附意见通过，4 个 P0 已修复，1 个新发现
- V3.1: 附意见通过，所有问题已修复
