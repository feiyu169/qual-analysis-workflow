# HeavySkill K8 审查结论：Qual v9 重构方案

**审查日期**：2026-08-23  
**审查方式**：HeavySkill 模式 2，K=8 轨迹并行推理 + 4 轨迹综合审议  
**截断状态**：0 截断，0 降级  
**总体结论**：**有条件通过**

---

## 核心判断

> 架构方向正确，但当前版本不具备按 11 周路线图直接实施的条件。
> 必须完成 6 项 P0 整改后才能进入 Phase 2 之后的正式开发。
> 若强行按原方案推进，最大失败点将从 v8 的"Gate4 死循环"转移为"报告质量不可接受"和"项目严重超期"。

---

## 8 轨迹收敛结论

| 收敛点 | 内容 |
|--------|------|
| 架构方向 | 四层分治正确，是对 v8 Gate4 死循环的合理回应 |
| 检查器精简 | 16→3 是最高风险决策，缺少覆盖矩阵和影子验证 |
| Gate4 | 单轮修复能降低死循环概率，但修复失败出口未定义 |
| 工期 | 11 周不现实，必须延长至 16 周 |
| 代码量 | 18,200 行未包含测试/可观测性/迁移工具，实际 22,000-28,000 行 |
| 生产可运营性 | 缺少可观测性/人工介入/灰度回滚/状态持久化 |
| 存储 | Wind MCP 是数据接口，不能替代审计日志/中间状态存储 |

## 6 项 P0 整改（必须完成后才能进入 Phase 2+）

### P0-1：冻结检查器 16→3 删除决策

**要求**：提交"旧 16 检查器 → 新 3 检查器"逐项覆盖矩阵：
- 每个旧检查器的去向：保留 / 合并 / 由确定性规则覆盖 / 由 LLM 生成质量承担 / 显式接受删除风险
- 保留旧检查器作为**影子模式运行**
- 至少覆盖小鹏 9868.HK 7 轮失败样本 + 20 个历史成功样本
- 建立漏检率基线，**A/B 通过后才允许删除旧检查器**

### P0-2：定义 Gate4 单轮修复的完整状态机

**要求**：Gate4 必须有明确出口：
- 修复通过 → 进入后续 Gate
- 修复失败但可接受 → 低置信度输出并转人工复核
- 修复失败且严重错误 → 终止并转人工队列
- 修复后必须再次通过 Layer3 终检
- 修复动作必须记录 diff、前后值、触发规则
- **禁止静默强制通过**

### P0-3：补齐轻量存储与审计能力

**要求**：保留轻量 storage adapter，至少持久化：
- 不可变输入快照（Wind 数据 + 财报解析结果）
- 检查结果（每个检查器的通过/失败/问题列表）
- 修复记录（修复前值/修复后值/触发规则）
- 最终版本和追溯信息

### P0-4：建立回归测试集与评估体系

**要求**：
- 以 9868.HK 7 轮失败样本为核心
- 加入历史成功报告样本
- 后续 prompt / 检查器 / 修复规则变更必须通过回归
- **没有回归集，无法证明 v9 真正解决 v8 问题**

### P0-5：重排工期

**要求**：总工期调整为 **16 周左右**（稳健区间 14-18 周）：
- Phase 2 增加 1-2 周用于检查器 A/B 编排
- Phase 4 增加 1 周用于 prompt 迭代
- Phase 5 拆分为数据层 2 周 + Gate5-8 至少 2 周
- Phase 6 集成测试至少 3 周
- 增加阶段 Go/No-Go 评审门

### P0-6：补充生产可运营性设计

**要求**：必须纳入：
- 结构化日志、trace_id、执行追踪、Gate 状态回放
- LLM 调用重试、超时、限流、降级、Token 预算
- 人工审核队列
- v8/v9 影子运行与灰度切换、回滚方案
- 状态持久化与断点续跑
