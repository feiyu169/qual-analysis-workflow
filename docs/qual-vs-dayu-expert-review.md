# Qual v8 vs Dayu Agent 三方专家综合审查报告

**审查日期**：2026-08-22  
**审查背景**：Qual v8 小鹏 9868.HK 全流程重跑 7 轮均失败（Gate4 死循环），需从架构层面诊断根因  
**对比对象**：[dayu-agent（大愚Agent）](https://github.com/noho/dayu-agent)——面向买方财报分析的 Agent 系统

---

## 一、三方共识：Qual 的根本问题

**三位专家一致认为：Qual v8 的核心问题是"过度工程化"——用程序化门禁对抗 LLM 的不确定性，但门禁本身的复杂度超过了 LLM 的不确定性。**

| 问题 | 架构专家诊断 | 代码专家诊断 | 投资专家诊断 |
|------|-------------|-------------|-------------|
| **Gate4 死循环** | 检查器间正反馈循环——修复一个问题触发另一个检查器误报 | `review_repair_loop` 4 层嵌套收敛判定，圈复杂度 CC≈35+ | 40-60 分钟未产出报告，买方不可接受 |
| **数据控制** | "检查器拦截修正"是事后补救，不是事前约束 | 数字提取逻辑三处并行（data_anchor / cross_chapter / numeric_binder） | LLM 仍会编造数字，PGNB 是事后补救 |
| **复杂度** | 16 个检查器 + 修复循环 = 不可控复杂度 | 57,000 行 / 262 文件，workflow.py 3,446 行 God File | 检查器越严格 → LLM 越难通过 → 耗时越长 |
| **架构范式** | Gate 状态机（固定 DAG）不适合 LLM 驱动的分析任务 | Legacy 单体 + v8 Gate 引擎双轨并行，循环依赖 | 需要"可控的效率"，而非"不确定的等待" |

## 三、根本差异：两种哲学

### Qual 的哲学："程序化约束 > LLM 自觉"
- 用 16 个检查器 + 修复循环确保质量
- 每个 Gate 有明确的准入/准出条件
- **问题**：检查器越多 → 误报越多 → 修复循环越长 → 耗时越长 → 检查器间正反馈死循环

### Dayu 的哲学："宿主强约束 > 模型自律"
- 数据访问被仓储协议强制接管，LLM 不能编造数字
- Session/Run/Attempt 三层生命周期，幂等性保障
- **优势**：从根源上杜绝"凭空捏造"，而非事后拦截修正

### 投资专家的核心判断
> **买方研究的核心矛盾是：数据必须 100% 准确，但 LLM 天然会编造数字。**
> - Qual 用程序化拦截解决这个问题（事后补救）——方向对但实现过度
> - Dayu 用"宿主强约束"解决这个问题（事前约束）——方向更对但实现不完整
> - **理想的系统应该结合两者：Qual 的报告结构 + Dayu 的数据控制范式**

## 五、架构专家重构路线图

### Phase 1（1-2 周）：消除重复
- ErrorType / FLOW_DEFINITION 合并到 `qual_v8/core/types.py`
- 数字提取层统一到 `qual_v8/core/numeric_extraction.py`
- 消除 cross_chapter_consistency / data_anchor / numeric_binder 三处重复

### Phase 2（2-4 周）：拆分 workflow.py
- `workflow_orchestrator.py`（编排入口，~300 行）
- `chapter_generator.py`（章节生成，~600 行）
- `data_collector.py`（数据收集，~400 行）
- `report_assembler.py`（报告组装，~200 行）
- `legacy_adapters.py`（适配层，~200 行）

### Phase 3（4-6 周）：引入 Agent 迭代模式
- 借鉴 Dayu 的"宿主强约束"——数据访问通过仓储协议，LLM 只能通过结构化接口读数据
- 简化 Gate 流水线：Gate3 章节生成 + Gate4 独立审计 + Gate8 终局（去掉 Gate5-7 的级联依赖）
- 引入增量修复：只重查受影响的章节，而非全量

### Phase 4（6-8 周）：质量保障升级
- 独立审计模型（借鉴 Dayu 的 audit/confirm/repair）
- 检查器分级：MUST_PASS（硬门禁）vs SHOULD_PASS（软建议）
- 端到端集成测试（减少 mock 依赖）

## 六、投资专家对理想系统的定义

| 层 | 要求 | 来源 |
|----|------|------|
| **数据获取** | 程序化获取（Wind + 巨潮 + SEC EDGAR），LLM 不参与 | Qual 的 Wind MCP + Dayu 的下载器 |
| **数据验证** | 程序化校验（数值范围、财年匹配、币值一致性） | Qual 的 PGNB（精简版） |

| **LLM 角色** | 只负责分析逻辑和写作，不负责数字 | Dayu 的"宿主强约束" |
| **质量保障** | 独立审计模型 + 增量修复 | Dayu 的 audit 模型 + Qual 的检查器（精简版） |
| **效率目标** | 晨会 15 分钟，深度 1 小时 | 买方实际需求 |

## 七、最终判断

**Qual v8 的问题不是"检查器不够多"，而是"检查器太多导致系统不可控"。**

从 7 轮全流程重跑的实测数据看：
- 每次修复一个问题，又暴露新问题——这是**过度工程化**的典型表现
- 16 个检查器 + 修复循环 + 全量重查 = 不可控复杂度
- Gate 级联依赖：一个 Gate 失败导致后续全部跳过

**Dayu Agent 的设计理念更正确**——"宿主强约束"从根源上解决数据可靠性问题，而非事后拦截。但 Dayu 的工程化不足（FMP 未实现、模板不足），需要完善。

**建议**：Qual 应从"程序化门禁"范式转向"宿主强约束 + 精简门禁"范式——保留报告结构和数据保障体系，但大幅简化检查器和修复循环，借鉴 Dayu 的仓储协议和独立审计模型。
