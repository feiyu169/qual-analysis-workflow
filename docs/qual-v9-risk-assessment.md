### 1.2 充分借鉴的项目（4/5 及以上）

#### ✅ contracts 层（4/5）

**借鉴内容**：
- frozen dataclass 替代 dict[str, Any]
- GateState 5 态状态机（对照 dayu RunState 7 态）
- CheckerProtocol / RepairerProtocol
- QualEvent / QualResult 事件系统
- CancellationToken

**评价**：V9 正确识别了 qual 需要的 5 项核心契约，规模从 dayu 的 5,373 行精简到 1,200 行（22%），这是合理的，因为：
- dayu 有 822 行的 `session.py`（多会话管理），qual 不需要
- dayu 有 721 行的 `agent_execution_serialization.py`（序列化层），qual 可简化
- dayu 有 318 行的 `toolset_config.py`（工具集配置），qual 工具集固定

**风险**：低。contracts 层是纯类型定义，不涉及业务逻辑，测试覆盖率可以做到 100%。

#### ✅ host 层（4/5）

**借鉴内容**：
- Gate 生命周期管理（executor + run_registry）
- 并发治理（concurrency）
- 事件发布（event_bus）
- Timeout 控制（deadline watcher）
- 熔断器（circuit_breaker）
- 审计日志（audit_logger）
- 第三方监督（supervisor）
- 错误分类（error_classifier）

**评价**：V9 正确识别了 qual 只需要 4 项能力（Gate 生命周期/并发/事件/Timeout），去掉了 5 项不需要的能力（Session/Cancel/Resume/多轮会话/Reply outbox）。这是 dayu 全量审查的核心结论之一。

**风险**：中。host 层是编排核心，涉及状态管理和并发控制，需要充分测试。

#### ✅ engine 层（4/5）

**借鉴内容**：
- 统一工具结果信封（tool_result）
- 参数校验器（argument_validator）
- 结构化事件模型（events）
- 协议抽象（protocols）

**评价**：V9 正确识别了 qual 是 Gate 顺序执行，不需要 AsyncAgent（2,093 行）/SSE 解析（990 行）/context budget（444 行）。只借鉴了 4 个核心概念，规模从 26,744 行精简到 5,200 行（19%）。

**风险**：低。engine 层是基础设施，不涉及核心业务逻辑。

#### ✅ storage 层（4/5）

**借鉴内容**：
- 3 个窄 Protocol（CompanyMeta + SourceDocument + ProcessedDocument）
- Factory 模式

**评价**：V9 正确识别了 dayu 有 6 个窄 Protocol，qual 只需要 3 个。这是 dayu 全量审查的核心结论之一。

**风险**：低。storage 层是纯接口定义，不涉及业务逻辑。

### 1.3 部分借鉴的项目（3/5）

#### ⚠️ write_pipeline（3/5）

**借鉴内容**：
- 报告写作流水线模式
- chapter_generator / prompt_builder / report_assembler

**遗漏内容**：
- ❌ 状态机驱动的章节执行（dayu `chapter_execution_coordinator.py` 561 行）
- ❌ 结构化审计决策（dayu `audit_rules.py` 1,190 行）
- ❌ 三步审计闭环（dayu `chapter_audit_coordinator.py` 570 行）
- ❌ 修复合同自动生成（dayu `repair_executor.py` 446 行）
- ❌ 过程状态追踪（dayu `pipeline.py` 1,543 行内 process_state）

**影响分析**：
- **状态机驱动**：dayu 的章节执行由状态机驱动（pending → generating → auditing → repairing → confirmed），每一步都有明确的状态转换和错误处理。V9 用硬编码循环替代，虽然更简单，但缺乏：
  - 状态持久化（如果中途失败，无法从断点恢复）
  - 状态可观测性（无法知道当前章节处于哪个阶段）
  - 状态转换校验（无法防止非法状态转换）

- **修复合同**：dayu 的修复器不是自由 patch，而是根据审计结果生成"修复合同"（明确指定要修复什么、怎么修复、修复到什么程度）。V9 的修复器直接根据 issues 列表修复，缺乏：
  - 修复范围约束（可能修复过度）
  - 修复效果可预测性
  - 修复历史可追溯性

- **过程状态追踪**：dayu 的 pipeline 会追踪每个章节的完整生命周期（生成→审计→修复→确认），包括每次操作的输入/输出/耗时。V9 没有引入，缺乏：
  - 执行过程可观测性
  - 性能瓶颈定位能力
  - 问题根因分析能力

**建议**：
1. **短期**（Phase 5 之前）：引入状态机驱动的章节执行，但简化实现（去掉 dayu 的 561 行，用 ~200 行实现核心功能）
2. **中期**（Phase 6 之后）：引入过程状态追踪，用于调试和性能分析
3. **长期**（v9.1）：引入修复合同，提高修复的可预测性

**风险**：中。遗漏的 5 个设计不是"nice to have"，而是 dayu 经过生产验证的核心设计。但考虑到 qual 的 Gate 模式比 dayu 的 Agent 模式更简单，遗漏的影响可控。

#### ⚠️ prompting（3/5）

**借鉴内容**：
- Prompt 模板构建（prompt_builder）
- 章节 prompt 模板
- 审查 prompt 模板

**遗漏内容**：
- ❌ scene manifest 继承（dayu `scene_manifest.py` 312 行）
- ❌ 条件渲染（dayu `conditional_renderer.py` 189 行）
- ❌ context_slots 收口（dayu `context_slots.py` 90 行）

**影响分析**：
- **scene manifest 继承**：dayu 的 prompt 不是独立的模板，而是通过 scene manifest 继承机制组织的。每个 scene 可以继承父 scene 的 prompt 片段，避免重复。V9 的 prompt 是独立的模板，可能导致：
  - prompt 片段重复（同一段话在多个章节的 prompt 中重复）
  - 修改不一致（修改一个 prompt 片段，需要手动同步到所有引用的地方）

- **条件渲染**：dayu 的 prompt 支持条件渲染（根据行业/市场/数据质量动态调整 prompt 内容）。V9 的 prompt 是静态模板，可能导致：
  - prompt 冗余（所有行业都用同一套 prompt，包含大量不相关的指令）
  - prompt 过长（静态模板为了覆盖所有情况，会包含大量条件分支）

- **context_slots 收口**：dayu 通过 context_slots 明确定义每个 prompt 需要哪些上下文数据，避免传入不必要的数据。V9 直接传入 DataContextContract，可能导致：
  - prompt 过长（包含不必要的上下文数据）
  - 数据泄露风险（敏感数据可能被传入不需要的 prompt）

**建议**：
1. **短期**（Phase 4 之前）：引入 context_slots 收口，明确每个 prompt 需要的数据
2. **中期**（Phase 5 之后）：引入条件渲染，根据行业/市场动态调整 prompt
3. **长期**（v9.1）：引入 scene manifest 继承，减少 prompt 重复

**风险**：低。prompt 是 LLM 的输入，不是程序逻辑，遗漏的影响主要体现在 prompt 质量上，不会导致程序错误。

### 1.4 "只学了皮毛没学到精髓"的风险评估

**结论：不存在"只学了皮毛没学到精髓"的风险。**

**理由**：
1. **V9 方案有明确的取舍逻辑**：V9 不是盲目照搬 dayu，而是根据 qual 的特点（Gate 模式、单次分析、无多会话）有选择地借鉴。dayu 全量审查报告明确指出："dayu ~192,000 行代码中，qual 实际只需要约 36,300 行（19%）"，V9 的 ~30,000 行目标与此一致。

2. **V9 保留了 qual 的核心优势**：V9 保留了 qual 的核心设计（Gate 模式、DataAnchor 锚点机制、PGNB 数字绑定、ADVC 锚点修复），这些是 qual 区别于 dayu 的核心竞争力。

3. **V9 消除了 qual 的核心缺陷**：V9 消除了 qual 的核心缺陷（Gate4 死循环、16 个检查器正反馈、dict[str, Any] 传递），这些是 dayu 全量审查报告中指出的关键问题。

4. **V9 有渐进式迁移方案**：V9 的 Phase 8 包含 A/B 测试和 v8 回退方案，不是一次性切换，降低了迁移风险。

**唯一需要注意的点**：write_pipeline 的状态机驱动和修复合同是 dayu 的核心设计，V9 遗漏了。但这不是"只学了皮毛"，而是"有意简化"——V9 用更简单的硬编码循环替代状态机，用更简单的 issues 列表修复替代修复合同。这种简化是合理的，因为 qual 的 Gate 模式比 dayu 的 Agent 模式更简单。

#### 新引入问题

1. **frozen dataclass 的可变性问题**：DataContextContract 是 frozen 的，但 anchor 是可变的（DataAnchor 需要被修改）。V9 方案中 `ctx.anchor` 是 `DataAnchor | None`，这违反了 frozen 的语义。
   - **建议**：将 DataAnchor 从 DataContextContract 中分离出来，作为独立参数传递。

2. **GateResultContract.chapters 的类型问题**：GateResultContract 是 frozen 的，但 `chapters: dict[int, str] | None` 中的 dict 是可变的。
   - **建议**：将 chapters 改为 `tuple[tuple[int, str], ...]`（frozen 的元组）。

3. **_VALID_TRANSITIONS 的完备性**：当前的状态转换表可能不覆盖所有合法场景（如 PENDING → FAILED）。
   - **建议**：参照 dayu 的 RunState 7 态，但简化为 5 态，并测试覆盖所有场景。

#### 技术风险

- **低**：contracts 层是纯类型定义，不涉及业务逻辑，技术难度低。

#### 回归风险

- **低**：Phase 0 不修改现有代码，只是新增 contracts 层，不会导致回归。

#### 人员风险

- **低**：contracts 层是纯类型定义，不需要领域知识，任何人都可以实现。

#### 时间风险

3. **Gate1 的类型推断规则**：V9 方案中 Gate1 的类型推断是规则引擎，但规则可能不覆盖所有行业。

- **中**：Wind MCP 接口和 PDF 解析是外部依赖，可能有不可预见的问题。

#### 回归风险

- **低**：Phase 1 是新增 Gate0/1/2，不修改现有代码，不会导致回归。

#### 人员风险

- **中**：需要了解 Wind MCP 接口和 PDF 解析，有一定的领域知识要求。

#### 时间风险

| **R2-6: 两周工期不足** | 3 个检查器，每个 200-500 行，可能需要更多时间 | 中 | 低 | 1. 优先实现 NumericGuard（最简单）<br>2. CrossChapterChecker 可延后到 Phase 3<br>3. 如果工期不足，Phase 2 可延长到 2.5 周 |

#### 新引入问题

1. **CrossChapterChecker 的锚点比对逻辑**：V9 方案中 CrossChapterChecker 的锚点比对逻辑是 `anchor.validate_chapter_any_fy(ch_num, content)`，但这个方法可能不存在（需要在 DataAnchor 中实现）。
   - **建议**：在 Phase 1 中实现 DataAnchor 时，同时实现 `validate_chapter_any_fy` 方法。

- **高**：迁移可能导致 v8 的功能退化，需要 A/B 测试验证。

#### 人员风险

- **低**：迁移是常规工作，不需要特殊的领域知识。

#### 时间风险

- **低**：4 个任务，每个 1-2 天，1 周足够。

## 三、维度三：整体方案的系统性风险

### 3.1 架构风险：四层分治是否引入了新的层间耦合？

**结论：四层分治是合理的，不会引入新的层间耦合。**

**理由**：
1. **层间依赖是单向的**：Layer 4 → Layer 3 → Layer 2 → Layer 1，没有反向依赖。
2. **层间接口是清晰的**：每层的输入输出都有明确的 contracts 定义（Phase 0 已实现）。
3. **层间通信是标准化的**：通过 DataContextContract 传递数据，不使用 dict[str, Any]。

**需要注意的点**：
- **DataAnchor 的可变性**：DataAnchor 在 Layer 1 初始化，在 Layer 4 被修改（ADVC 修复），这违反了 Layer 1 的"只读"原则。
  - **建议**：将 DataAnchor 从 DataContextContract 中分离出来，作为独立参数传递，明确其可变性。

### 3.2 数据流风险：Layer 1→2→3→4 的数据传递是否清晰？

**结论：数据传递是清晰的，但有 2 个潜在风险。**

**风险 1：DataContextContract 的版本兼容性**
- **描述**：DataContextContract 在不同 Phase 中可能被修改（如 Phase 0 定义，Phase 1 添加字段），修改可能破坏向后兼容性。
- **概率**：中
- **影响**：中
- **缓解措施**：
  1. DataContextContract 的修改需要向后兼容（新字段有默认值）
  2. 使用版本号标识 DataContextContract 的版本
  3. 测试覆盖所有版本的 DataContextContract

**风险 2：chapters 的传递**
- **描述**：chapters 在 Gate 间传递（Gate3 生成 → Gate4 检查 → Gate5 增强 → Gate6 结论），但 chapters 的格式可能在不同 Gate 中不一致。
- **概率**：低
- **影响**：中
- **缓解措施**：
  1. chapters 的格式在 contracts 中明确定义（`dict[int, str]`）
  2. 每个 Gate 独立验证 chapters 的格式
  3. 测试覆盖所有 chapters 传递场景

### 3.3 回退风险：如果重构失败，能否回退到当前状态？

**结论：回退方案是完整的，风险低。**

**理由**：
1. **v8 代码保留**：V9 方案不删除 v8 的代码，只是新增 v9 的代码。
2. **v8 配置保留**：V9 方案不修改 v8 的配置，只是新增 v9 的配置。
3. **A/B 测试**：Phase 8 包含 A/B 测试，可以在 v8 和 v9 之间切换。
4. **Git 历史**：所有改动都在 Git 中，可以随时回滚。

**需要注意的点**：
- **Phase 0 删除 18 个文件**：Phase 0 会删除 18 个文件（~3,300 行），这些文件可能被其他模块引用。
  - **建议**：删除前检查依赖，删除后运行全量测试。

### 3.4 渐进性风险：能否边重构边运行（渐进式迁移），还是必须一次性切换？

**结论：可以渐进式迁移，不需要一次性切换。**

**理由**：
1. **Phase 0-7 是新增代码**：Phase 0-7 不修改现有代码，只是新增 v9 的代码。
2. **Phase 8 是 A/B 测试**：Phase 8 同时运行 v8 和 v9，比较结果。
3. **Phase 8 是平滑切换**：Phase 8 在 A/B 测试通过后，平滑切换到 v9。

**需要注意的点**：
- **Phase 2 精简检查器**：Phase 2 会删除 13 个检查器，这可能影响 v8 的功能。
  - **建议**：Phase 2 不删除旧检查器，只是新增 3 个新检查器。在 Phase 8 的 A/B 测试通过后，再删除旧检查器。

### 3.5 测试风险：现有 456 个测试中有多少会在重构中失效？如何保证测试覆盖？

**结论：测试风险中等，需要妥善处理。**

**分析**：
1. **现有测试数量**：qual_v8 有 1 个测试文件，quality 有 28 个测试文件，总计 29 个测试文件（不是 456 个）。
2. **测试失效原因**：
   - Phase 0 删除 18 个文件，可能导致引用这些文件的测试失效
   - Phase 2 精简检查器，可能导致引用旧检查器的测试失效
   - Phase 4 新增章节生成，可能需要新的测试

3. **测试覆盖保证**：
   - Phase 0 新增 contracts 层的测试（~300 行）
   - Phase 2 新增检查器的测试（~400 行）
   - Phase 4 新增章节生成的测试（~400 行）
   - Phase 5 新增 Gate4 的测试（~300 行）
   - Phase 7 新增 E2E 测试（~400 行）+ 金标准测试（~400 行）

**缓解措施**：
1. **渐进式重构**：Phase 0-7 不修改现有代码，只是新增代码，不会导致现有测试失效。
2. **Phase 8 的 A/B 测试**：Phase 8 同时运行 v8 和 v9，比较结果，确保 v9 不差于 v8。
3. **测试覆盖率监控**：使用 pytest-cov 监控测试覆盖率，确保覆盖率 ≥80%。

## 五、建议的调整项

### 5.1 高优先级调整（必须做）

#### 调整 1：Phase 2 不删除旧检查器

**当前方案**：Phase 2 删除 13 个检查器  
**建议方案**：Phase 2 只新增 3 个检查器，不删除旧检查器。在 Phase 8 的 A/B 测试通过后，再删除旧检查器。

**理由**：
- 降低回归风险
- 允许渐进式迁移
- 如果新检查器有问题，可以快速回退到旧检查器

#### 调整 2：引入 write_pipeline 的状态机驱动

**当前方案**：write_pipeline 使用硬编码循环  
**建议方案**：引入状态机驱动的章节执行（简化版，~200 行）

**理由**：
- dayu 的状态机驱动是核心设计，经过生产验证
- 状态机可以提供状态持久化、状态可观测性、状态转换校验
- 简化版实现可以控制复杂度

#### 调整 3：引入 context_slots 收口

**当前方案**：prompt 直接传入 DataContextContract  
**建议方案**：引入 context_slots，明确每个 prompt 需要的数据

**理由**：
- 避免 prompt 过长（包含不必要的上下文数据）
- 避免数据泄露风险（敏感数据可能被传入不需要的 prompt）
- dayu 的 context_slots 是核心设计，经过生产验证

### 5.2 中优先级调整（建议做）

#### 调整 4：将 DataAnchor 从 DataContextContract 中分离

**当前方案**：DataAnchor 是 DataContextContract 的字段  
**建议方案**：DataAnchor 作为独立参数传递

**理由**：
- DataAnchor 是可变的，违反 frozen dataclass 的语义
- 分离后可以明确 DataAnchor 的可变性
- 分离后可以更容易地测试 DataAnchor 的修改

#### 调整 5：将 GateResultContract.chapters 改为 frozen 类型

**当前方案**：GateResultContract.chapters 是 `dict[int, str] | None`（可变）  
**建议方案**：GateResultContract.chapters 改为 `tuple[tuple[int, str], ...]`（frozen）

**理由**：
- GateResultContract 是 frozen 的，但 chapters 是可变的，违反 frozen 的语义
- frozen 的 chapters 可以防止意外修改
- frozen 的 chapters 可以安全地在并发环境中使用

#### 调整 6：引入过程状态追踪

**当前方案**：没有过程状态追踪  
**建议方案**：在 Phase 6 之后，引入过程状态追踪

**理由**：
- 过程状态追踪可以提供执行过程可观测性
- 过程状态追踪可以帮助定位性能瓶颈
- 过程状态追踪可以帮助分析问题根因

### 5.3 低优先级调整（可选做）

#### 调整 7：引入 scene manifest 继承

**当前方案**：prompt 是独立的模板  
**建议方案**：在 v9.1 中，引入 scene manifest 继承

**理由**：
- 减少 prompt 片段重复
- 提高 prompt 的可维护性
- dayu 的 scene manifest 是核心设计，但复杂度较高

#### 调整 8：引入修复合同

**当前方案**：修复器根据 issues 列表修复  
**建议方案**：在 v9.1 中，引入修复合同

**理由**：
- 提高修复的可预测性
- 提供修复范围约束
- dayu 的修复合同是核心设计，但复杂度较高

#### 调整 9：引入条件渲染

**当前方案**：prompt 是静态模板  
**建议方案**：在 v9.1 中，引入条件渲染

**理由**：
- 根据行业/市场动态调整 prompt
- 减少 prompt 冗余
- dayu 的条件渲染是核心设计，但复杂度较高
