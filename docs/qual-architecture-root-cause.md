# Qual v8 架构根本问题诊断（2026-08-22）

## 一、现象：一份报告跑 40+ 分钟仍失败

| 轮次 | 耗时 | 结果 | 核心阻断 |
|------|------|------|---------|
| 第3轮 | ~30min | ❌ Gate4 失败 | 空壳章死循环 |
| 第4轮 | ~40min | ❌ Gate4 失败 | 数字回滚死循环 |
| 第5轮 | ~45min | ❌ Gate4 失败 | 日期锚点循环 |
| 第6轮 | ~47min | ❌ Gate4 失败 | 跨章一致性 77 issues |
| 第7轮 | ~47min | ❌ Gate4 失败 | 现金流占位符残留 |

**每次修复一个问题，又暴露新问题**——这是架构级缺陷的典型表现。

## 二、根本问题：Gate 状态机 + LLM 重写 = 不可控复杂度

### 问题 1：审查修复循环是"LLM 对抗 LLM"

```
Gate3: LLM 生成章节 → 检查器发现问题 → LLM 重写 → 检查器又发现新问题 → ...
Gate4: LLM patch 修复 → 校验失败 → 回滚 → LLM 再 patch → 又失败 → ...
```

**本质**：用 LLM 修复 LLM 的错误，但 LLM 每次重写都可能引入新错误（数字幻觉、模糊时间词、格式违规）。检查器越严格，LLM 越难通过，重试越多，耗时越长。

### 问题 2：检查器数量爆炸（165 个文件，33,000 行）

qual 的质量保障层包含：
- 5 个 numeric guard 闸门（量级/空章/空壳/财年/币值）
- cross_chapter_consistency（财务数据+结论+时间三类检查）
- fact_checker（事实核查）
- conclusion_validator（结论合理性）
- depth_reviewer（分析深度）
- assumption_checker（假设合理性）
- date_anchor_check（日期锚点）
- structural_check（结构检查）
- logic_consistency_check（逻辑一致性）
- data_reasonableness_check（数据合理性）
- PGNB（数字回填+裸数字拦截+语义检测）
- ADVC（锚点驱动数值清洗）
- FiscalSemantics（财年语义）

**每个检查器都可能误报**，误报触发 LLM 重写，重写又触发新误报。这是**检查器间的正反馈循环**。

### 问题 3：数据流设计——"全量重查"vs"增量修复"

当前架构：每轮修复后，**所有检查器对所有章节全量重查**。这意味着：
- 修复 ch5 的数字 → ch6/ch7 的跨章一致性可能变化
- 修复 ch7 的日期 → ch5 的结论一致性可能变化
- 修复 ch10 的格式 → 所有章节的占位符检查可能变化

**没有"变更影响范围"的概念**——每次修复都是全局震荡。

### 问题 4：Gate 级联依赖——一个 Gate 失败全部跳过

```
Gate4 失败 → Gate5 跳过 → Gate6 跳过 → Gate7 跳过 → Gate8 跳过
```

Gate8 的终局 sweep（ADVC + PGNB + 日期绑定）是"最后防线"，但因为前置依赖被跳过。我们刚修了这个（Step 4.7 独立运行终局 sweep），但这只是补丁——**级联依赖本身就是架构问题**。

### 问题 5：LLM 调用次数不可控

一轮全流程的 LLM 调用：
- Gate1: 事实提取（3 年 × 多批次）≈ 5-8 次
- Gate3: 11 章 × (1 生成 + 0-3 重试) ≈ 11-44 次
- Gate4: 审查修复循环 × (事实核查+深度审查+结论审查+修复 patch) ≈ 10-30 次
- Gate5-7: 估值/结论/概览 ≈ 5-10 次
- **总计：30-90 次 LLM 调用**，每次 10-30 秒 → 5-45 分钟

而 dayu-agent 的设计：**Agent 迭代模式**，LLM 自主决定何时调用工具、何时停止，不需要预设的 Gate 流水线。

## 四、核心反思

qual 的设计哲学是"**程序化门禁 > LLM 自觉**"——用 16 个检查器 + 修复循环确保质量。这在理论上是正确的（CFA/新财富水平的报告需要严格质量控制），但实践中导致了：

1. **复杂度爆炸**：检查器越多 → 误报越多 → 修复循环越长 → 耗时越长
2. **LLM 对抗 LLM**：用 LLM 修复 LLM 的错误，但 LLM 每次重写都可能引入新错误
3. **全量重查震荡**：修复一个章节可能影响所有章节的检查结果
4. **Gate 级联脆弱**：一个 Gate 失败导致后续全部跳过

**可能的架构方向**：
1. **简化 Gate 流水线**：减少检查器数量，合并同类检查
2. **Agent 模式**：让 LLM 自主决定分析步骤，而非预设固定 DAG
3. **增量修复**：只重查受影响的章节，而非全量
4. **检查器分级**：MUST_PASS（硬门禁）vs SHOULD_PASS（软建议），减少误报对流程的影响
5. **单次生成 + 程序化后处理**：LLM 生成一次，程序化处理所有数字/日期/格式问题，不依赖 LLM 重写
