## 0. 结论摘要

根因文档的**核心判断成立**：三层嵌套重试 × 确定性 LLM 空输出 = 指数级耗时，且审查-修复循环无收敛判定的确是不收敛的根。但文档有三处**必须修正**：① Gate 级重试并非"叠乘"而是冗余约束；② 复杂度公式算术错误（4×3×10×3×3×90s = 27 小时，不是 162 小时）；③ "70-120s 超时"是措辞误导——`finish=max-tokens + text=""` 不是超时，是**推理模型输出预算耗尽**（确定性失败），与 R6 的流中断（瞬态失败）是两类错误，修复策略完全不同。

更严重的是，代码验证发现了**文档完全遗漏的 6 个架构级缺陷**：Gate 熔断器因枚举类型不匹配而**永不触发**（死代码）；`spec.timeout` 在运行时**零处强制**（全流程无墙钟边界）；检查器→修复器**契约不对称**（修复验证器集 ⊂ 审查验证器集，且问题无结构化身份）；修复**诱导回归**（58→50→61→88 震荡）无单调性守卫；审计日志无问题级/调用级粒度且**无检查点恢复**；shadow 模式语义泄漏 + 失败报告**静默产出**未修复章节。

修复优先级（成本/收益/风险详见第 4 节）：**必须立即做**——① LLM 空输出按 finish 分类、确定性失败不重试；③ shadow 模式跳过重试 / Gate4 仅重试 1 次；④ 全局墙钟预算并真正强制执行；F 修正 shadow 语义；S2 最小版（轮次趋势早停 + 单 Gate 调用次数硬上限）。**尽快做**——模型-任务匹配（短结构输出换非推理模型/提预算）、问题清单驱动 + 结构化 issue 契约、单调性守卫。**可延后**——调用级熔断器、检查点/结构化审计、假阳性自学习豁免。

## 2. 架构结论验证

### 2.1 三层嵌套重试——结构判断正确，三处修正

**结构判断正确**：LLM 调用层（3 次尝试）× Gate4 内循环（3 轮）× Gate 级重试（3 次重试=4 次执行），且各层独立设上限、乘积无上限。这是本次死循环的骨架，文档抓住了。

三处修正：

1. **Gate 级不是"叠乘"**。`WorkflowConfig.max_retries=3`（workflow.py:37）与 `GateSpec.max_retries=3`（gate4.py:72）是**同一层级的两个冗余闸门**：`while attempts < max_attempts`（workflow.py:261）与 `gate.can_retry()`（gate_engine.py:59-61，`retry_count < spec.max_retries`）必须同时成立才继续，实际效果是 **min(3,3)=3 次重试 → 4 次执行**。真正做乘法的不是这两者，而是内层：4 次执行 × 3 轮 × ~35 次调用/轮 × 3 次尝试/调用。
2. **熔断器不会在第 4 次前截断**（详见 D5）：`record_failure` 因枚举类型不匹配永不计数。所以"4 次完整执行"是成立的——但不是因为熔断器没生效，而是**熔断器本身就是死代码**。
3. **"叠乘"若真发生会更糟**：如果未来有人把 WorkflowConfig.max_retries 调到 5，Gate 执行次数仍被 GateSpec 卡在 4；反之亦然。两层上限耦合但语义不清，这是设计气味——应明确"Gate 级重试由谁说了算"。

### 2.2 总复杂度估算——结构对、算术错、参数低估

- **算术错误**：文档公式 `4×3×10×3×3×90s` = 97,200 s = **1,620 分钟（27 小时）**，文档写成"9720 分钟（162 小时）"，高估 **6 倍**。结论方向不变（27h 理论最坏仍远超任何可接受预算），但 6 倍误差会误导修复效果评估。
- **参数低估**：每轮 LLM 调用不是"每章 2-4 次"。按代码实算每轮：
  - 深度审查 `check_depth`：每章 1-2 次（>20000 字符按段分批，`depth_reviewer.py:238-257`）→ 10-20 次
  - 结论审查 `check_conclusion`、假设审查 `check_assumptions`：各 1-2 次
  - 对抗辩论：3 章 × 3 角色 ≈ 9 次（`debate_service.py:27,39-40`，`review_repair_loop.py:236-262`，**无 enable_debate 开关**）
  - 修复 `_repair_chapters`：有问题章节数（通常全部 10 章）× 1 次
  - **合计约 30-45 次/轮**，且每次失败调用 = 3 次尝试 × ~90s
- **修正后的最坏估算**：4 × 3 × 35 × 3 × 90s ≈ **113,400s ≈ 31.5 小时**；若全部失败走"3 次尝试"，仅失败尝试的耗时就达 108×3×~88s ≈ 8 小时（与实测 6+ 小时吻合——日志证实 Gate4 从 02:11 空转到 07:10，约 5 小时纯审查-修复空转）。
- **可操作的量级论证**（支撑第 4 节优先级）：
  - 只做 S1（确定性失败不重试）：最坏 ≈ 4×3×35×90 ≈ 10.5h（仍过长）
  - S1 + S3（Gate4 单次执行）+ S2 最小版（~1.5 轮早停）+ C（空输出率 48%→5%）：≈ 1×1.5×35×(0.95×30s+0.05×90s) ≈ **25-30 分钟**——回到合理量级。这就是"哪些必须立即做"的定量证据。

## 3. 设计缺陷补充（文档 4 条之外）

### D1. 桥接 ok 语义把两类失败混为一谈（最根本的契约缺陷）

`plugins/llm-bridge.js:57-64`：

```js
ok = finishReason === 'stop'   // 非 stop 一律 ok=false
```

`harness_llm.py:110-115` 再把 `ok=False` 统一 raise 后重试 2 次。但 `finish=max-tokens + text=""` 与 R6 的流中断（`ok=False, finish=null`）是**两类完全不同的失败**：

- **流中断**（R6，42 次）：宿主流式处理被掐断，partial text 丢失 → 瞬态，重试有意义；
- **预算耗尽**（本次 106 次）：deepseek-v4-flash 是推理模型（`docs/qual-llm-timeout-direct-api.md:29`），长 prompt（修复 prompt 嵌整章，日志实测 7K-32K 字符）下思考 token 吃光 12000/8000 输出预算，产出 0 可见文本 → **对同一 prompt+model 是确定性的**，重试 3 次纯属浪费 4.5 分钟/次。

**修复必须按 finish reason 分类**，不能笼统"空输出不重试"（那会连瞬态流中断的重试也砍掉）。同时桥接侧应区分 `finishReason` 语义（`max-tokens`/`stop`/`error`/`null`）。

### D2. 检查器→修复器契约不对称（不收敛的第二根源）

- 检查器产出**自由文本问题**（`review_repair_loop.py:123` `issue.description`），无 issue_id、无位置 span、无期望值、无验证器引用；修复器靠正则 `第(\d+)章` 猜章节（`review_repair_loop.py:283-289`），**匹配不到章节号的问题被静默丢弃**（不计入 chapter_issues，但下轮照报）。
- 修复验证器只有 3 个：structural / consistency / numeric（`review_repair_loop.py:364-391`）；而每轮审查跑 9 类检查器（跨章、逻辑、合理性、估值仲裁、日期锚点、事实、深度、结论、假设、辩论）。**修复验证器集 ⊂ 审查验证器集** → 一个 patch 可能通过全部修复校验、却完全没解除原 issue，下轮原 issue 照报。
- **结构性缺陷不可修复**：深度审查的"缺敏感性分析""缺行业对比"（`depth_reviewer.py:154-162`）要求**新增内容**，而 patch 协议（`patch_applier.py:26` MAX_PATCHES=5，`review_repair_loop.py:342-348` "只修复点名的位置，未点名的一个字节都不要动"）结构性禁止新增 → 即使 issue 是真的，也**永远修不掉**。文档把这类归为"假阳性"不准确：它们是**真问题但协议上不可修复**，比假阳性更糟（假阳性还能豁免，这类只会永久失败）。

### D3. 零容忍通过判据在统计上不可达

`review_repair_loop.py:71` 以 `round_issues == 0` 为通过标准。任何检查器（规则或 LLM）都有非零假阳性率；叠加 D2 的不可修复类问题，**通过概率趋近 0，期望通过时间趋近 ∞**。必须改为"趋势 + 容差"判据（问题数单调下降且低于阈值），而不是归零。

### D4. 修复诱导回归，无单调性守卫

修复是有耦合的随机扰动：修 ch6 数字对齐锚点 → ch7 引用旧数字变不一致 → 下一轮问题数反而上升（日志 58→50→61→88 的震荡来源）。`patch_applier` 只校验**单章局部**校验器，**从不校验"全报告问题总数是否下降"**；任何"修复后问题数增加"的轮次都不回滚。审查-修复循环没有"进展度量"，只有"是否归零"。

### D5. Gate 级熔断器是死代码（双重失效）

1. **枚举类型不匹配**：`error_classifier.py:15-19` 与 `circuit_breaker.py:24-28` 各自定义 `ErrorType` 枚举；`workflow.py:305` 把 `classification.error_type`（error_classifier 的枚举）传给 `record_failure`（比较 circuit_breaker 的枚举）。Python 跨类枚举比较恒为 False → `record_failure` **永远不计数** → 熔断器永远不打开。
2. **即使计数，权重也到不了阈值**：`classify_from_exception`（error_classifier.py:99-114）对 `RuntimeError`（Gate4 的错误都是 RuntimeError 包装）落到 `UNKNOWN_ERROR` → 默认 TRANSIENT（+0.5）；阈值 3 需要 6 次连续失败，而 Gate 循环最多 4 次执行（3 次失败记录）→ 熔断器在单次运行内**结构上不可能触发**。
3. 附带：`record_failure` 对 BUSINESS 类型**不计数**（circuit_breaker.py:51-58），而"审查未修复/逻辑矛盾/风险覆盖不足"恰恰该归 BUSINESS——设计意图与实现完全相反。

结论：**"熔断"在 Gate 层不存在**。文档中期方案第 5 项（"已有雏形，但未覆盖 harness_llm 内部重试"）严重低估了差距——现有雏形（run 脚本 fallback）与真正的熔断器之间还差着分类、位置、半开探测三层。

### D6. 全流程无墙钟边界（spec.timeout 是装饰）

`gate_engine.py:79-111` 的 `execute_gate`、`workflow.py:258-311` 的重试循环**全程没有任何超时执行代码**：无 `asyncio.wait_for`、无 `signal.alarm`、无线程 watchdog。所有 Gate 的 `spec.timeout`（Gate4=1200s）在运行时**零处被读取**。文档"只约束单次 execute"的说法不成立——它什么都不约束。本次 6h 卡死得以发生，正是因为系统里**唯一的墙钟边界是单次 HTTP 调用的 300s/240s 超时**，而循环只由"次数"约束。

### D7. 无检查点/恢复，审计粒度不足

- `audit_logger.py:65-115` 只记 Gate 级事件（workflow_started/gate_started/gate_completed），**无问题级、无修复结果级、无调用级**；本轮问题签名、修复成败、回滚原因只在 `.pip-tmp/llm-calls.log` 纯文本里，无 run_id/issue_id 关联。
- 章节内容全程在内存 dict 中，报告只在**流程最后**写盘（`run_xpev_full.py:253`）——宿主一重启（本次 07:10 即如此），6 小时工作全部丢失，无 resume 入口。
- 结果对象自欺：`ReviewRepairResult.issues_found` 跨轮累计、`issues_fixed` 按**章节**计（有 patch 应用即 +1，非"问题解除"）、`remaining_issues` 只含最后一轮 → **从结果对象无法度量收敛**。

### D8. shadow 模式语义泄漏 + 失败报告静默产出

- shadow 只影响 `workflow.py:350-359` 的 raise，重试循环（258-311）与模式无关 → "记录不阻断"变成"记录但照样全量烧钱"。
- Gate4 失败后（shadow 不阻断），`workflow.py:365-374` 仍会从原始 chapters **静默组装"快速报告"**返回——一份未修复、未审查、可能含占位符的报告被打包产出，无任何"shadow 失败"标记；下游 Gate5-8 以"前置 Gate 4 未通过"（gate_engine.py:87-98）连锁失败，真实原因被掩盖。
- 这是合规风险：研究流水线的输出应显式携带质量状态，而不是静默降级。

### D9. 已知卡死的辩论组件在收敛关键循环里无条件运行

技能纪律明示"辩论机制 enable_debate=False（已知卡死问题）"，且 `gate5.py:202` 确实遵守了开关；但 `review_repair_loop.py:236-262` 的审查辩论**绕过开关**，只要 review_caller 非空就无条件跑 3 章 × 3 角色（≈9 次调用，单角色 240s 上限，重试 1 次）——一个已知会卡死的组件，被放在收敛关键的内层循环里。日志证实：`bear_ch5/bull_ch4/bear_ch4` 全是 max-tokens 空输出重试。

### D10. 每轮重建审查调用器 + 更小的 max_tokens

`review_repair_loop.py:182-194` 每轮 `create_harness_caller(max_tokens=8000, ...)` 新建审查 caller；8000 的预算比主 caller 的 12000 更小，**推理模型空输出概率更高**（日志中 depth_review/bear 等审查调用正是失败主力）。

### D11. LLM 失败被静默转换为假问题 / 检查器异常被吞成"通过"

- `depth_reviewer.py:283` 解析 LLM 输出失败时默认返回 **50 分** → `final_score < 60` → 制造"第N章分析深度不足"假问题。空输出 → 假问题 → 假问题去修复 → 空 patch → 下轮再现。这是"假阳性"的一个隐蔽来源：**审查层的 LLM 失败被翻译成了业务问题**。
- 反方向同样危险：`_run_deep_review`/`_run_substantive_review` 里**每个检查器**都被 try/except 吞掉（review_repair_loop.py:124-125 等），检查器崩溃=静默贡献 0 问题；`gate4.py:278-280` 实质审查整体异常时直接 `{"passed": True}`——**fail-open**：LLM 全挂时 Gate4 反而"通过"，产出零修复的报告。重试到死（fail-closed 过度）与静默通过（fail-open）两个方向的错误同时存在。

### D12. 运行指标口径混乱

`223 开始 / 201 完成 / 108 失败` 三数不自洽（201+108≠223）。日志证实 失败=逐尝试记录（一次调用可记 3 次失败）；开始=调用级。没有结构化指标（attempt 序号、耗时、finish reason、prompt 大小、round 序号）落库，6 小时的复盘只能靠 grep 文本日志。这直接削弱了"无幂等失败识别"的可观测性基础——**你不知道失败分布，就无法设计熔断**。

## 5. 架构原则建议（LLM 流水线通用）

1. **先分类，后重试**。重试只对瞬态错误有意义。错误至少分四类：瞬态（网络/流中断/限流，可重试+退避）、确定性（预算耗尽/格式错误/空输出，不重试，改策略：换模型/拆任务/降级）、语义失败（ok 但内容不合格，走业务处理）、熔断触发（跳过）。分类依据放在**最靠近故障源**的层（桥接/调用器），用 finish reason + 异常类型，而不是统一 Exception。
2. **嵌套重试只算乘积，不算各层上限**。任何多层重试（调用×任务×流程）都必须有：(a) 全局墙钟预算；(b) 总调用次数预算；(c) 单层上限语义明确（冗余约束还是乘积）；(d) 可观测的剩余预算。本次事故的本质是"每层都有上限，但它们的乘积没有"。
3. **LLM 输出契约显式化、结构化、带后置条件**。空输出/截断/解析失败要有明确语义与异常类；调用器强制"非空后置条件"；JSON 任务用 schema 校验而不是"找第一个 { 到最后一个 }"（`patch_applier.py:47-50`）。契约脆弱性直接放大成重试风暴。
4. **质量闭环要清单驱动 + 单调性**。修复目标 = 冻结的问题清单；修复后只验证清单内问题 + 无新回归；问题数上升的修复轮必须回滚；通过判据用"趋势 + 容差"而非"归零"——任何检查器都有假阳性率，零容忍的期望通过时间是 ∞。
5. **检查器与修复器共享同一契约**。issue 必须带结构化字段（id/位置/期望值/验证器引用）；修复验证器集必须 ≥ 审查验证器集（或至少能判定"该 issue 是否解除"）；"真问题但协议上不可修复"（结构性缺陷）必须在设计期识别并分流（新增内容 → 走重写路径，不是 patch）。
6. **熔断器放在真正的故障源，且要真的会开**。位置：LLM 调用层（按错误类别计数）、数据源层；Gate 级熔断若分类不对就是死代码。熔断状态跨运行持久化（连续多轮同型失败才可信）；半开探测必须存在，否则"切直连"是一次性决策。
7. **降级必须带语义标记**。shadow/degraded 产出必须显式打标（"未修复/未审查/部分失败"）并附问题清单，绝不静默产出看似正常的报告；失败原因要随报告传递，不许变成下游"前置 Gate 未通过"的笼统报错。
8. **长任务必须可恢复、可复盘**。阶段化持久化（每 Gate 落盘）、结构化审计（round/issue/调用三级）、resume 入口。"6 小时跑完才写结果"的设计不允许存在；本次宿主一重启，6 小时工作归零。
9. **模型-任务匹配是最被低估的杠杆**。短结构输出（patch JSON、评分、分类）用非推理模型或小思考预算；长文写作才用推理模型 + 大预算。用 finish reason 分布做任务级监控：`max-tokens 空输出率` 超阈值 → 自动调 maxTokens/换模型/告警。这次 48% 的空输出率本质是"用推理模型干格式任务的错配"。
10. **一切可观测**。每次调用的 attempt/finish/耗时/prompt 大小、每轮问题签名与修复结果、每次回滚原因，都进结构化指标——否则死循环只能靠事后 grep 猜，熔断/收敛/调参全都无从谈起。
